# ServeSmart project review — 2 November 2026

**Overall assessment.** ServeSmart has a substantial implementation of restaurant POS, purchasing, inventory, and administration. It is currently an integration and stabilization project: many screens and controllers exist, but several essential journeys are broken or inconsistent. The current source is not ready for a production release. Fix the build, access controls, and sale-to-stock-to-cash reconciliation before expanding the feature list.

**Scope.** Reviewed both `RestaurantDemo_Frontend` and `RestaurantDemo_Backend`, including routing, models, controllers, permission handling, checkout calculations, reporting, layout, and project configuration. The frontend uses React 19, TypeScript, Vite, and Tailwind; the backend uses Express, TypeScript, Mongoose, and MongoDB. There are 142 frontend source files and 100 backend source files.

**Verification limits.** Build, lint, and existing unit tests were executed. Chrome was used at 1440 × 1000 and 390 × 844 with intercepted local sample API responses and an isolated browser profile. This verifies frontend rendering and layout, not real authentication, database writes, actual stock reconciliation, or printer/payment hardware. The configured backend/database was not started or changed. Existing source edits were preserved. Screenshots contain sample business data.

**Release blockers — resolve these first.**

1. **The frontend cannot produce a release build, and four important routes crash.** The duplicate `catch` is the first blocker, not the only one. Browser checks confirmed `PackagePlus is not defined` on Create Purchase, `currencyCode is not defined` on Sales/Purchase Reports, and `toBusinessDateInputValue is not defined` on Z-bill. Additional diagnostics identify missing menu helper exports and undefined product detail calculations (`avgMargin`, `totalProfit`). Fix the full diagnostic set and add an error boundary so one faulty screen does not erase the application shell. Evidence: [offer service](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/services/specialOfferService.ts:40), [Create Purchase](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/purchases/CreatePurchase.tsx:1142), [Sales Report](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/reports/SalesReport.tsx:241), [Z-bill](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/reports/ZBillReport.tsx:16).

2. **Administrative settings and some business mutations lack authentication.** `/api/settings/mail` GET/POST, `/api/settings/system` GET/PUT, and legacy receipt GET/POST routes have no auth middleware. The mail controller returns the complete settings document, including the stored SMTP password when configured. Profile update trusts a caller-supplied `userId`; purchase creation also lacks an authentication check. Sale-return and purchase-return delete endpoints likewise have no authentication in their route/controller path. This conclusion accounts for authentication embedded in controller arrays elsewhere; a route lacking visible middleware is not automatically classified as public. Protect every sensitive endpoint explicitly, use the authenticated identity for profile/creator fields, and return allowlisted settings fields. Evidence: [settings routes](D:/Qdesk/resturant/RestaurantDemo_Backend/src/routes/settingRoutes.ts:30), [mail response](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/mailSettingController.ts:10), [profile controller](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/userController.ts:18), [purchase route](D:/Qdesk/resturant/RestaurantDemo_Backend/src/routes/postRoutes.ts:79), [return deletion routes](D:/Qdesk/resturant/RestaurantDemo_Backend/src/routes/deleteRoutes.ts:57).

3. **Product permissions are explicitly bypassed, and role management uses competing permission systems.** Both frontend `hasPermission` and backend permission middleware automatically allow `manageProducts`. Meanwhile, backend middleware reads `RolePermissions` by `user.role`, whereas role-edit screens/controllers update `Role.permissions` via `roleId`. Checks also mix `create/read/update/delete` with action names such as `create_role/view_role`. Role endpoints can require both incompatible styles. Choose one permission source and one action vocabulary, remove the product exception, and verify that changing a role changes actual API access. Evidence: [backend bypass](D:/Qdesk/resturant/RestaurantDemo_Backend/src/middleware/permissions.ts:23), [frontend bypass](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/contexts/PermissionContext.tsx:199), [RBAC lookup](D:/Qdesk/resturant/RestaurantDemo_Backend/src/config/rbac.ts), [role controller](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/roles&Permissions/index.ts:37).

4. **Deleting a Z-bill deletes the session's actual sales.** Both single and bulk deletion call `Sale.deleteMany` and remove sessions. The single handler requires authentication but no explicit delete permission or ownership check; bulk deletion uses a view-sales permission. These paths do not reverse stock deductions. Prefer preserving closed financial records and using controlled void/refund/correction entries. Any administrative deletion facility needs a distinct permission and a consistent inventory/audit policy. Evidence: [single deletion](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:707), [bulk deletion](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:751), [bulk route permission](D:/Qdesk/resturant/RestaurantDemo_Backend/src/routes/postRoutes.ts:48).

5. **Environment files are tracked by Git.** Both repositories return `.env` from `git ls-files`; the backend file contains configuration keys for MongoDB, JWT, first-run setup, and an admin password. Values were not printed or included in this review. Remove sensitive environment files from tracking, provide safe examples, and rotate any real credentials that have been shared through repository history. Adding an ignore rule alone does not untrack an existing file.

**Correctness and workflow issues — complete these before a pilot.**

6. **The main POS path skips prepared-food ingredient deduction.** `/pos/sale` calls `applyMainStockDeductionForSale` only. Regular completed sales also call kitchen validation and `processRecipeInventoryDeduction`. Consequently, prepared items can bypass recipe availability checks and ingredient consumption through the primary POS route. Use the same sale-completion service for both entry points. Evidence: [POS deduction](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:501), [regular sale deduction](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/sale/index.ts:964).

7. **The selected POS warehouse is not used for the sale.** The UI loads warehouse-specific catalog prices, but its checkout payload omits `warehouseId`; the backend selects the first active warehouse. A cashier can view warehouse B and consume stock from warehouse A. Include and authorize the selected warehouse and price all lines from that warehouse. Evidence: [POS payload](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/pos/POSCheckout.tsx:1585), [backend warehouse lookup](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:412).

8. **POS prices and offer discounts are trusted from the client.** The backend reads each item's `price` and a supplied `specialOfferDiscount` instead of resolving current authorized prices/offer rules. Authentication alone does not prevent a modified request from changing those values. The same path records every line's cost and the sale's profit as zero. Resolve product/variation prices, costs, offer eligibility, and calculated totals on the server; require a separate permission and audit record for price overrides. Evidence: [POS calculations](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:438).

9. **Tendered cash and change are not reconciled correctly.** The main POS accepts an amount greater than the total and displays change, while the backend stores the full tender as `cashAmount`. Register closing adds those amounts directly. For a 950 sale paid with 1,000 cash and 50 change, this path adds 1,000 to expected cash instead of 950. Register/dashboard aggregations also omit sale-status filtering in several places, allowing cancelled/returned records into totals. Record cash tendered, change, refunds, and net drawer movement separately; define how each transaction state contributes to reports. Evidence: [payment submission](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/pos/POSCheckout.tsx:1546), [stored payment totals](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:467), [register closing](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:543), [dashboard aggregates](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/dashboard.ts:110).

10. **POS and regular sales apply different discount/tax rules.** Regular sales multiply a fixed sale discount by total quantity, apply tax, then add shipping. POS subtracts the fixed discount once and includes shipping in the taxable base. Three units with a fixed discount of 10 therefore receive discounts of 30 and 10 respectively. Define the intended business rules, label them clearly, and centralize the calculations. Use currency-safe rounding/minor-unit calculations and test boundary cases. Evidence: [shared frontend calculations](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/utils/saleCalculations.ts:44), [regular backend calculation](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/sale/index.ts:74), [POS calculation](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:461).

11. **POS invoice IDs can collide across dates and table reuse.** Takeaway/delivery counters reset daily, but persisted IDs are only `T-001`/`D-001`, with no date. Dine-in uses the table identifier as the invoice identifier when supplied. `Sale.invoiceId` is globally unique, so the same daily sequence on a later date or another sale for the same table can fail. Separate a globally unique invoice ID from a short display ticket number and table reference. Evidence: [ticket generation](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/pos/index.ts:387), [unique invoice schema](D:/Qdesk/resturant/RestaurantDemo_Backend/src/models/Sale.ts:96).

12. **Sale-return creation is not connected, and backend refund limits need work.** The frontend posts to `/sale-returns`, but the POST router never registers `createSaleReturn`. The existing controller also does not enforce return quantity against the remaining sold quantity; it matches an original line only by product ID and marks the whole sale returned even for partial returns. Wire the endpoint with authentication/permissions, identify exact product/variation lines, cap cumulative returns, calculate refunds from the original net paid price, and distinguish partial/full returns. Evidence: [UI submission](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/sales/CreateSaleReturn.tsx:229), [POST router](D:/Qdesk/resturant/RestaurantDemo_Backend/src/routes/postRoutes.ts), [return controller](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/saleReturn/index.ts:120).

13. **Repeated and partially failed operations need stronger protection.** The primary checkout has no submission-in-progress lock, and `/pos/sale` has no request idempotency key. Purchasing explicitly disables transactions; some paths use read/modify/save stock updates. Main-stock deductions do use conditional atomic decrements and compensation, and kitchen deduction has transaction/fallback logic, but the complete sale/payment/main-stock/kitchen-stock operation is not one atomic workflow. Add request idempotency, prevent repeat clicks, and test failures between each write. Use transactions where supported or a durable recovery design for standalone deployments. Evidence: [checkout handler](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/pos/POSCheckout.tsx:1546), [purchase transaction choice](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/purchaseController.ts:18), [main stock deduction](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/sale/index.ts:332), [kitchen deduction](D:/Qdesk/resturant/RestaurantDemo_Backend/src/controllers/kitchen/deduction.ts:188).

14. **Visible actions and navigation imply unfinished functionality.** Hold only alerts; View Menu has no handler; Register Reports points to `/reports_register`, whose route is commented out. The fallback sends unknown URLs to login, which obscures broken links. The collapsed sidebar renders group initials but prevents opening groups. Finish these actions or hide them until usable; add a real not-found page and route-level permission handling. Evidence: [Hold](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/pos/POSCheckout.tsx:1506), [View Menu](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/pos/POSCheckout.tsx:1936), [sidebar](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/util/sidebar.tsx:63), [missing report route](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/App.tsx:320).

15. **Reports need business validation, not just visual polish.** Inventory Report stores From/To dates but never applies them. It reads warehouse `productQty` and does not total variation-level quantities, so variation inventory can appear as zero. A historical stock report needs movement/snapshot data rather than current product quantities. POS profit is zero and dashboard/register status filters are inconsistent, so revenue/profit/stock totals should not yet be used as authoritative operational figures. Evidence: [inventory report](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/reports/InventoryReport.tsx:31).

16. **Uploads need restrictions.** The general `/api/upload` endpoint is unauthenticated and Multer has no configured size or file-type restrictions. Uploaded files are publicly served. Add authentication, permissions, size limits, a validated image allowlist, safe decoding/re-encoding where appropriate, and cleanup for replaced files. Evidence: [upload endpoint](D:/Qdesk/resturant/RestaurantDemo_Backend/src/server.ts:64).

17. **Configuration and dormant code can reintroduce broken flows.** Purchase create/edit hardcode `http://localhost:5000/api`. The offer service uses `/specialOffers` instead of the mounted `/special-offers` and reads a session-storage token while login writes local storage. The currently unconnected `CheckoutPage` can report demo success without saving an order. Keep one supported POS/checkout flow; remove or isolate old/demo code and use one configured API client with consistent auth/error handling. Evidence: [purchase API URL](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/purchases/CreatePurchase.tsx:76), [offer service](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/services/specialOfferService.ts:15), [dormant checkout fallback](D:/Qdesk/resturant/RestaurantDemo_Frontend/src/components/pos/CheckoutPage.tsx:392).
